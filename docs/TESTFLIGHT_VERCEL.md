# Vercel setup for TestFlight

## Deploy the candidate

1. Confirm the beta qualifies as personal, non-commercial use under Hobby and keep the hosting budget at £0. Check the current included usage before inviting testers. [Hobby plan](https://vercel.com/docs/plans/hobby) · [Fair Use Guidelines](https://vercel.com/docs/limits/fair-use-guidelines)
2. In Vercel, import `calixtan123/NextBranch` from GitHub. Use repository root `.`, the Next.js preset, Node.js 24.x, install command `npm ci`, build command `npm run build`, and the preset's default output directory. [Build configuration](https://vercel.com/docs/builds/configure-a-build) · [Supported Node.js versions](https://vercel.com/docs/functions/runtimes/node-js/node-js-versions)
3. In Project Settings → Environment Variables, add `TFL_API_KEY` with Type set to Secret for Production. Add it separately for Preview only if you need live Preview checks. Redeploy the affected environment after changing the key. Keep it out of `NEXT_PUBLIC_*` and `EXPO_PUBLIC_*` variables, logs, and evidence. [Vercel environment variables](https://vercel.com/docs/environment-variables) · [Secret environment variables](https://vercel.com/docs/environment-variables/sensitive-environment-variables)
4. Use `main` as the production branch after the PR merges, or explicitly promote the reviewed candidate. Confirm the production deployment has the expected SHA and Production variables. Assign a stable HTTPS production domain under Project Settings → Domains. Use Standard Protection to protect previews and generated deployment URLs while allowing unauthenticated access through the production domain. Test that domain from a signed-out client without cookies or bypass headers. The native bundle needs only the stable origin. [Project settings](https://vercel.com/docs/project-configuration/project-settings) · [Promotion](https://vercel.com/docs/deployments/promoting-a-deployment) · [Deployment Protection](https://vercel.com/docs/deployment-protection)

## Publish the shared rate limit

In Firewall → Configure → Custom Rules, add one rule for the **Request Path** with **Matches expression** `^/api/(departures|journey)/?$`. The expression shares one budget across both paths and their trailing-slash variants. Leave Hostname unconstrained so all project domains and aliases match, including the default Vercel production alias and any reachable deployment or preview URL. Inventory those URLs and verify each is covered by the rule or blocked by Deployment Protection. [WAF custom rules](https://vercel.com/docs/vercel-firewall/vercel-waf/custom-rules) · [Rule configuration](https://vercel.com/docs/vercel-firewall/vercel-waf/rule-configuration)

Select **Rate Limit**, review the pricing dialog if shown, then set **Fixed Window**, **IP**, **60 requests**, **60 seconds**, and **Too Many Requests (429)**. Select **Save Rule**, **Review Changes**, then **Publish**. Check the published rule in Firewall. Hobby includes one rate-limit rule per project and currently lists one million allowed rate-limit requests. Review WAF allowed requests, edge requests, transfer, invocations, CPU, and memory in Usage during the beta. [WAF rate limiting](https://vercel.com/docs/vercel-firewall/vercel-waf/rate-limiting) · [Usage dashboard](https://vercel.com/docs/pricing/manage-and-optimize-usage) · [Hobby limits](https://vercel.com/docs/plans/hobby)

Five active testers watching three stations each at a 30-second interval generate about 30 departure requests per minute before initial loads, manual refreshes, and web journey traffic. Testers behind shared Wi-Fi or carrier NAT share an IP budget. Regional counters and distributed clients allow aggregate traffic to exceed 60 requests per minute. A departures request can fan out to several line/stop feeds, while a journey can fetch two arrival feeds plus topology and timetable on cache misses. The initial limit is provisional. Confirm the actual TfL subscription and allowance for the production key, then compare measured traffic and fan-out against that entitlement before expanding the beta. [Regional counters](https://vercel.com/i/rate-limiting-algorithms) · [TfL API products](https://api-portal.tfl.gov.uk/products)

## Verify the production origin

Run these from a signed-out connection against the stable domain with `origin` set to its HTTPS origin. Record status, headers, and redacted body samples. Expect `200` JSON and `Cache-Control: no-store` for the two live calls. Confirm the requested station or journey identity and live timestamps or valid empty data. Expect `400` JSON with `INVALID_STATION` or `INVALID_JOURNEY` for the invalid requests. [HTTP verification](VERIFICATION.md)

```sh
curl -sS -i --max-time 25 "$origin/api/departures?station=940GZZLUCTN"
curl -sS -i --max-time 25 "$origin/api/journey?from=940GZZLUCTN&to=940GZZLUEGW"
curl -sS -i --max-time 10 "$origin/api/departures?station=invalid"
curl -sS -i --max-time 10 "$origin/api/journey?from=invalid&to=invalid"
```

Use one test IP and quiet window. First confirm both invalid requests reach validation and return 400. Then send at most 65 requests in a short burst, alternating the same invalid queries across the two paths so each path stays below 60 by itself. Stop the burst at the first 429, then make one invalid probe for each path and slash variant within that same window to confirm they also return 429. The invalid inputs return before any TfL calls even if they reach the app. Keep redirects unfollowed when testing slash variants so a Next.js redirect does not hide the WAF result. If the burst crosses a window boundary, wait for the counter to reset and repeat once within a single window. Repeat coverage checks for reachable aliases in separate windows. [WAF rate limiting](https://vercel.com/docs/vercel-firewall/vercel-waf/rate-limiting)

Record UTC time, host, path, region and request identifier if available. Match the 429 to the published rule in Firewall and check Runtime Logs for the same request or narrow time range. Use the allowed 400s as positive controls for function invocation. A matching WAF block with no corresponding function invocation shows that the blocked request never entered the handler that calls TfL. A 429 response alone is insufficient evidence. Capture its content type, body shape, and Retry-After if present. [Firewall observability](https://vercel.com/docs/vercel-firewall/firewall-observability) · [Runtime Logs](https://vercel.com/docs/logs/runtime)

Wait for both the WAF window and the client retry deadline to expire. Confirm an invalid request returns 400 again and repeat a valid live request. In a separate controlled check, load a valid snapshot in the client before using invalid requests from the same IP to exhaust the WAF budget. Confirm the client retains that snapshot on 429, avoids retries during its cooldown, then clears the error and shows fresh data after recovery. Web accepts a positive Retry-After delta or standard HTTP date. Native uses positive delta seconds. Both can fall back to a valid JSON interval or 30 seconds when needed. [Candidate verification](TESTFLIGHT_VERIFICATION.md)

## Build, migrate, and roll back

Set `EXPO_PUBLIC_NEXTBRANCH_API_URL` in the EAS `production` environment to the stable HTTPS origin without a path, query, or fragment. This value is bundled into the app. Keep fixture variables, TfL credentials, and Vercel bypass tokens out of the release bundle. Follow the repository's EAS and Apple signing instructions for the production build and App Store Connect submission. [Native signing and submission](../native/README.md#testflight-release-build) · [EAS environment variables](https://docs.expo.dev/eas/environment-variables/) · [Expo iOS production builds](https://docs.expo.dev/tutorial/eas/ios-production-build/)

Inventory the Netlify origin in every distributed binary. If it uses an owner-controlled domain, cut its DNS over only after Vercel TLS, API, and WAF checks pass, then verify the same origin from an old binary. If it uses a Netlify-owned hostname, continuity depends on recovering Netlify access and keeping the old endpoint working or configuring and testing forwarding there. Verify query strings, status, cache and retry headers, and effective WAF behavior through any proxy. Keep Netlify preview protection in place and verify that the old production URL still works without a password or login. If suspension prevents continuity, record which builds are affected and distribute a replacement signed build with the Vercel origin. [Netlify redirects and proxies](https://docs.netlify.com/manage/routing/redirects/rewrites-proxies/) · [Netlify protection](https://docs.netlify.com/manage/security/secure-access-to-sites/password-protection/)

For an app regression, use Vercel Instant Rollback to restore the previous production deployment on Hobby, then rerun the smoke checks on the stable domain. Rollback restores the previous build and its environment. For a firewall regression, revert the WAF rule separately and publish the change. Promote the fixed deployment to restore automatic production domain assignment after a rollback. During a DNS cutover, retain a tested reversal path where the previous origin remains available. [Instant Rollback](https://vercel.com/docs/instant-rollback) · [WAF custom rules](https://vercel.com/docs/vercel-firewall/vercel-waf/custom-rules)

### Later migration from Vercel to Netlify

1. Deploy the reviewed Next.js candidate to Netlify before changing traffic. Set `TFL_API_KEY` as a secret in the Production context for the Functions runtime and redeploy. Keep it out of client variables and evidence. Protect previews and keep the production API accessible without a login, password, or bypass token. [Next.js on Netlify](https://docs.netlify.com/build/frameworks/framework-setup-guides/nextjs/overview/) · [Function environment variables](https://docs.netlify.com/build/functions/environment-variables/) · [Secret variables](https://docs.netlify.com/build/environment-variables/overview/) · [Netlify protection](https://docs.netlify.com/manage/security/secure-access-to-sites/password-protection/)
2. Confirm that the available Netlify rate limits provide equivalent protection before cutover. Verify a shared budget for `/api/departures` and `/api/journey` and cover slash variants and all reachable aliases, including `netlify.app`. Account for per-domain counters and enforcement delay. Adapt the signed-out smoke and controlled invalid-query burst above to the configured limit and delay. Check live JSON and `Cache-Control: no-store` on both routes, invalid JSON errors, and uncached host-generated 429s. Record any `Retry-After`, confirm blocked requests skip the function, and verify client cooldown and recovery. Keep traffic on Vercel if these checks fail. [Netlify rate limiting](https://docs.netlify.com/manage/security/secure-access-to-sites/rate-limiting/)
3. Inventory the origins embedded in shipped builds. For an owner-controlled custom domain, add it to Netlify, save the previous DNS records, and switch DNS after the Netlify checks pass. Verify TLS and repeat the signed-out API and rate-limit checks on the custom domain after DNS resolves to Netlify. For a `vercel.app` origin, keep that Vercel endpoint serving the API or test an external rewrite to the protected Netlify origin before switching it. Check both routes through the old URL, including query strings, status, cache and retry headers, and effective rate limiting. Confirm continuity in an already-shipped build on a physical iPhone over Wi-Fi and mobile data. [Netlify external DNS](https://docs.netlify.com/manage/domains/configure-domains/configure-external-dns/) · [Netlify HTTPS](https://docs.netlify.com/manage/domains/secure-domains-with-https/https-ssl/) · [Vercel external rewrites](https://vercel.com/docs/routing/rewrites)
4. If the embedded origin changes, update `EXPO_PUBLIC_NEXTBRANCH_API_URL`, distribute a new signed production build, and repeat the physical-device checks. Record any affected old builds if their URL cannot be kept working. Retain the known-good Vercel deployment and WAF during the transition. On failure, restore the old DNS records or roll back the forwarding deployment, then repeat the signed-out API and physical-device checks on the restored origin. Keep the new origin working for any replacement builds already distributed. [Native signing and submission](../native/README.md#testflight-release-build)
