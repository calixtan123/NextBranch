## UI and interaction scope

1. **Home.** NextBranch heading with top-right Search; Saved platforms heading and n/3 count; Manage platforms action and Settings icon. Vertically scrolling stack of zero to three rounded, compact platform cards. Each card shows station name, direction and verified platform, line marker/name, next three departure rows and freshness footer. Tapping a card opens that exact platform's detail. Add a platform is available below capacity; search remains available at capacity. Empty launch explains how to add the first platform. Pull down/hold to refresh provides visible progress and a non-gesture accessible refresh action.
2. **Departure board.** Back navigation and Platform departures title; station/platform identity; up to five departures using the same data/filter/order and visual style as the home card; Save platform/Saved and Refresh. Display the actual number available, including fewer than five or none. Back retains saved order and current preferences.
3. **Search and platform picker.** Station-name search, offline canonical names/aliases, clear/no-match states, and the two most recently selected distinct stations when the query is empty. Selecting a station updates recents and opens physical platform/direction selection. Require a reviewed platform tuple before opening/saving a board. Back/Cancel preserves saved selections. Use the real catalogue, not the prototype's fixed 12-station list or universal A/B platforms.
4. **Manage/replace platforms.** Reorder with a drag handle plus accessible move actions; remove with five-second Undo; tap a saved item to edit its display. At capacity, saving another platform opens a replacement flow naming the incoming and existing selections, with explicit confirmation and cancellation. Replace only the chosen slot. Exact duplicates never consume another slot.
5. **Settings and appearance.** Settings exposes Appearance and Manage cards. Appearance offers **Custom for each card**, **Amber for all**, and **Modern for all**, with visible/accessible selected state. Custom mode links to Manage card styles. Card display identifies the selected station/direction/platform and offers Amber or Modern; choosing one switches global mode to Custom. Preserve individual choices when switching temporarily to a global style. The expanded board uses the same effective style as its card.
6. **Visual treatment.** Preserve the design's dark charcoal surfaces, subtle borders, compact rounded card shells, sans-serif headings and right-aligned countdowns. Amber uses warm dot-matrix destination/via/countdown text over a dark dotted board; Modern uses pale blue readable text and blue row rules over a dark dotted board. Rows show ordinal, destination, advertised via/branch and minutes/Due. Keep the station/direction/platform and line label outside the departure display. Use shared style tokens, with the design's colours as reference: dark background #0B0B0D, surface #171719, foreground #ECEDEF, muted #929398, border #303033, amber #FFAA25, Modern text #BDEBFF. Support light/dark using the existing specification and the prototype's light palette; a manual theme switch is not present in the reviewed screen flow. Use real system safe areas/status/home indicator, without drawing the prototype's phone bezel or fake 9:41 status bar.

## Required behaviour and acceptance criteria

* \[ \] Launch restores zero to three unique ordered selections keyed by canonical `(stationId, platform, direction)`. A new installation starts empty. Cards, order, board-style mode, per-card styles and two recent stations persist across process restart using validated/versioned local preferences. Read/write failures leave the session usable and visibly explain any persistence limitation.
* \[ \] Six fixture trains produce three Home rows and five detail rows from the same station snapshot. Filter exact platform/direction and expire rows before sorting/limiting; the next eligible train fills an expired row. Show all advertised branches. Preserve destination and Bank/Charing Cross wording together at small widths and large text sizes, rather than clipping essential route information. Missing destination/branch has explicit fallback text, including Branch unavailable.
* \[ \] Due/expiry follows the preparation specification: countdown derives from expected arrival; Due extends through -30 seconds inclusive, then the train disappears. Any clock times use Europe/London. Unassigned platform predictions do not appear under a confirmed platform and are disclosed separately where relevant.
* \[ \] Saving Colindale and two Camden physical platforms starts exactly two distinct-station requests. Same-station cards share observation time, snapshot and polling. Expanding a fresh saved card reuses its snapshot. One station's failure does not replace or clear another station's healthy state.
* \[ \] Cards/detail provide distinct loading, fresh-empty, unavailable, offline, stale, refreshing, retry and recovery states. Fresh empty copy is “No departures currently assigned to this platform”. Freshness uses actual observedAt, with age >30 seconds stale, or a matching refresh failure/offline condition. Retry retains the warning until accepted success; never clear stale status just because refresh was tapped. Respect the existing 20-second deadline, server polling interval (30-second fallback), 10-second per-station manual cooldown and shared server 429 delay. Pause background polling and recompute expiry on resume. Late responses cannot restore a removed/replaced selection.
* \[ \] Search → station → verified physical platform → detail → Save works online and with fixture transport; bundled search/catalogue remain usable offline. Empty/no-match, unknown catalogue and cancelled selection remain recoverable. Do not infer a physical platform from a branch or from absence/presence of predictions.
* \[ \] Save/reorder/remove/Undo/replace and rapid repeated actions preserve the three-card limit and identity invariant. Duplicate save returns to the existing selection. Cancel replacement writes nothing. Undo restores the removed selection/position without rolling back unrelated edits; if the slot has since been filled, request an explicit replacement choice before displacing anything.
* \[ \] All three appearance modes work on Home and detail. Editing one card changes only that card's stored override and switches the effective mode to Custom. Preference changes survive relaunch; global style changes preserve existing custom overrides.
* \[ \] Core flows work on small and large iPhones, portrait/landscape, with keyboard visible, light/dark, maximum Dynamic Type and Reduce Motion. VoiceOver reads meaningful train/card text and selected options; dot-matrix glyph dots are decorative. Controls have at least 44 × 44 point targets; reorder/removal/Undo work without dragging; refresh completion is announced once without announcing every countdown tick.
* \[ \] Update product/design documentation to describe the implemented platform-card flow and record framework/setup commands, design reference, verification evidence and remaining limitations.

## Prototype gaps to address deliberately

The reviewed component starts with three hardcoded sample platforms; all trains/times are static; refresh is simulated; state is in-memory; stale is global; search/platform metadata are placeholders; sample IDs differ from picker-generated IDs; replacement is immediate on tapping a card; Undo restores an entire old list without expiry; several Back actions jump to Home; and long departure text is clipped/shrunk. These are prototype limitations, not production requirements. Preserve the visual intent while meeting the acceptance criteria above. Do not render “Updated just now” for old data or “5 upcoming trains” when fewer exist.

Sample A/B platform labels must remain explicitly synthetic in fixture/demo mode. The real Colindale/Camden physical-platform catalogue and directions require reviewed provenance before live acceptance. Line-colour entries for additional lines in the prototype do not establish multi-line product scope; use the existing supported station/line data.
